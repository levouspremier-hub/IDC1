### 7.2 服务损失的具体原因（**定位结论**）

1. **raw 提案是「全组满请求」**（20 组 compute 全 1.0），而 **exec 动作被投影成稀疏极值点**：
   前 5 组为 0（`raw→exec` 最大修正 1.0 即由此而来）。由
   `offset = (1/N)·Σ_g |u_g − raw_g|` 在 `u_g ≤ raw_g` 时恒等于 `N − Σ_g u_g`
   ⇒ **Stage A 的「最小 L1 偏移」在数学上等价于「最大化总分配量」**；
   在可行域为多面体时，最优解落在**顶点** ⇒ 求解器给出「少数几组吃满、其余为 0」的
   角点解，而**总工作量并不小**（Stage A 目标 0.8477 ≈ 20−Σu，即 Σu ≈ 19.15 ⇒ 近似满额）。
2. 环境侧 `planned_capacity_vec[g] = action[g] × …`：exec 只在少数组上非零
   ⇒ **参与服务的服务器组大幅减少**，env 自身的任务分配器只能在少数组内安置任务。
3. 当步到期的**不可中断**任务 `2515224290600144462`（剩余 3.518，`deadline=4`）
   因此**未获得任何工作量** ⇒ 被记为不可中断中断；
   `deadline_shortfall_work = 3.5179` 与其剩余工作**完全一致**，即该损失被规划器
   「看见」并作为风险标记，但 Stage B 的 tie-break 仍选择了该角点解。
4. **corrector off 的同一 raw 提案（20 组全 1.0）直接进入环境**，服务器组全开 ⇒
   服务完美（按时率 1.0 / 剩余 0 / 中断 0），**且两种模式四类物理违规均为 0**
   ⇒ 损失**不是**由接入 / SOC / 守恒约束造成，而是由**投影的取解形状**造成。

**候选原因归属**：支持「**修正器投影**」（最强）与「**任务分配顺序**」（下游表现）；
**不支持**「容量 / 接入限制」（接入有余量、off 同动作服务完美）。

**仍未定位**：角点解是在 Stage A 的 MIP 求解中产生，还是在 Stage B 的 tie-break /
取整阶段产生（两者 status 均为 `optimal`）；需要在实施修复时用消融实验分别定位。
