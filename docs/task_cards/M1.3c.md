### 2.2 ⚠️ 核心缺口：`build_scenario_from_true()` 会把未来真值装进 forecast

`scenario/scenario.py:49-83`：

```python
def build_scenario_from_true(split, start, horizon, forecast_cutoff, true, ...):
    """从真值数组构建切片；只物化 `[0, forecast_cutoff)` 的可见预测（拷贝，非视图）。"""
    def _window(key: str) -> list[float]:
        return [float(x) for x in np.asarray(true[key])[:forecast_cutoff]]   # ← 65-66 行
```

它把传入的 `true` 数组**前 cutoff 个元素**直接当作 `*_forecast`。函数本身
**没有任何机制**保证这 cutoff 个元素来自「时刻 t 可获得的预测」——
调用方传整段真值它就照抄。**这正是「未来真值切片后改名预测」。**

同一问题出现在 planner 侧，`planning/snapshot_adapter.py:128-134`：

```python
price_forecast=_visible_window(env.price_t, t, cutoff, horizon),   # ← 读的是真值数组
load_forecast=[0.0] * cutoff,  # 系统负荷未建模，声明边界假设      # ← 129 行：全零冒充
pv_forecast=_visible_window(env.pv_t, t, cutoff, horizon),
...
```

即 planner 看到的「可见预测」**就是** `env.price_t/pv_t/wt_t/T_amb/carbon_factor_t`
在 `[t, t+cutoff)` 的真值；而 `load_forecast` 是**全零数组**静默充当预测。

**窗口之外**的扩展是可信的：`snapshot_adapter.py:26-30` 的 `EXTENSION_POLICY` 明确写
「窗口外规划假设……不读未来真值」，`_series()`（`snapshot_adapter.py:65-71`）只读
`[t, t+n_visible)`，窗口外用持久化/保守 0 填充。**越界不泄漏是成立的；越界以内是真值冒充。**

## 3. 连续切分方案（2024：366 天 = 17,568 个半小时点）

**共同约束**（三方案均满足）：

- **不随机打散**时间序列，严格连续；
- 任一 episode/horizon **不得横跨 split 边界**：采样起点 `t ≤ split_end − H`；
- **边界约束按 origin 表达（M1.3d 勘误，取代原「统一 `H+C` purge」）**：
  三段 truth **完整覆盖 17,568 行、不丢行**；不预设统一 purge。
  约束是:
  - episode origin：`origin_index + H <= row_end_exclusive`；
  - forecast origin：`origin_index + C <= row_end_exclusive`；
  - **若 `H >= C`，不得重复扣除 `C`**（`H+C` 是错的双重惩罚）；
  - 模型 lookback **只允许读 origin 之前**的数据；
  - **是否需要统计学 purge，由具体 forecast 模型的 lookback/label 定义决定**，
    不得预先写死 `H + C`。
- **闰日 Feb 29 全部落在 train**（三个方案的 train 都从 1 月 1 日起、跨过 2 月）；
- 归一化参考值**只在 train 上冻结**，val/test 永不重算；
  **该冻结最迟必须在 M1.3g 训练接线前完成，不能推迟到 M6**（原表述已勘误）。

| 方案 | split | 起止 | 天数 | 行数 | 占比 |
|---|---|---|---|---|---|
| **A 严格 60/20/20** | train | 2024-01-01 → 2024-08-07 | 220 | 10,560 | 60.1% |
| | val | 2024-08-08 → 2024-10-13 | 67 | 3,216 | 18.3% |
| | test | 2024-10-14 → 2024-12-31 | 79 | 3,792 | 21.6% |
| **B 月对齐** | train | 2024-01-01 → 2024-07-31 | 213 | 10,224 | 58.2% |
| | val | 2024-08-01 → 2024-09-30 | 61 | 2,928 | 16.7% |
| | test | 2024-10-01 → 2024-12-31 | 92 | 4,416 | 25.1% |
| **C 长训练** | train | 2024-01-01 → 2024-09-11 | 255 | 12,240 | 69.7% |
| | val | 2024-09-12 → 2024-10-26 | 45 | 2,160 | 12.3% |
| | test | 2024-10-27 → 2024-12-31 | 66 | 3,168 | 18.0% |

三者的天数与行数合计均为 **366 天 / 17,568 行**（已核算）。test 天数分别
79 / 92 / 66，均 **≥ 30 个不同测试日**（满足 `IMPLEMENTATION_PLAN` §12 M9.2）。

### 3.1 唯一推荐：**方案 B（月对齐）**

| 维度 | 评价 |
|---|---|
| 边界可审计性 | **最好**：切分点落在**自然月边界**，人工可肉眼核对，无需解释「8 月 8 日」这类任意日 |
| 闰日归属 | Feb 29 完整落在 train，无歧义 |
| 季节覆盖 | train 覆盖 1–7 月（东北季风尾 + 西南季风），val 8–9 月，test 10–12 月（年末东北季风）；三段季节不重叠 |
| 边界 | 切分点落在自然月边界；episode / forecast origin 的约束按 §3 的 origin 规则逐条校验 |
| 测试独立性 | test 为**连续 92 天**、与 train/val 无任何重叠窗口，≥ 30 天 |
| 与 60/20/20 的偏差 | 58.2/16.7/25.1；**偏离**计划书的字面 60/20/20，但月对齐带来的可审计性与闰日无歧义更值钱，且计划书的 60/20/20 是**指导值**，最终由 M9.2 人工冻结 |

**不推荐 A**：切分点落在 8 月 7 日 / 10 月 13 日这类月中日期，与自然月边界不对齐，
审计时要额外解释；换来与 60/20/20 更接近，收益有限。
**不推荐 C**：val 仅 45 天，模型选择方差大；train 占比偏高会削弱 test 的季节代表性。

> ⚠️ **本卡不创建 split manifest**；方案 B 需**人工确认**后才在 M1.3d 落地。

## 4. forecast 口径（逐类外生量）

三类必须**严格区分并在契约中可判定**：

- **truth**：M1.3b canonical 历史事实（`row_count=17568`，逐值原样，含 signed IGS）。
  只允许作为**执行时**环境真值与**评估**参照，**不得**进入 observation/planner 当预测。
- **forecast**：在时刻 t **实际可获得**的预测，必须带 `generated_at`、可见窗口、
  模型 revision 与 seed。
- **oracle**：未来真值复制，**只允许显式 debug / upper-bound**，**禁止**进入正式训练、
  评估或任何主结果。

| 方案 | 当前可实现 | 需新增数据 | `generated_at` | horizon | seed / model revision | 泄漏风险 | 允许进入正式训练/评估 |
|---|---|---|---|---|---|---|---|
| **A 外部真实预测产品** | ❌ 不可 | ✅ 需（价格/负荷的官方或第三方**历史预测**存档；天气可用预报再分析） | 产品自带发布时刻 | 产品定义 | 产品版本号 | 低（真实可得信息） | ✅（数据到位后） |
| **B 训练历史拟合/校准的 persistence / seasonal-naive** | ✅ **可实现**（只用 train 段） | ❌ 不需要 | **切片起点 t**（由 generate 时显式写入） | 1..H | `seed` + 拟合代码 revision + 训练范围 | **中**：必须在 train 上拟合/校准参数，**不得**用 val/test；naive 基线**天然**只用 t 及以前 | ✅（参数与范围冻结后） |
| **C oracle-debug** | ✅ 可实现 | ❌ 不需要 | t | 1..H | 无 | **最高**（就是真值） | ❌ **仅 debug**，产物必须标 `oracle_debug=true` 并在 report 显式声明 |

**逐序列的最低要求**（M1.3e 落地，本卡只定口径）：

| 序列 | truth 来源 | 可接受的 forecast（在 A 不可得时） | 明确禁止 |
|---|---|---|---|
| `price` | canonical `price_sgd_per_kwh` | B：seasonal-naive（同时刻历史中位数）+ 明确 `generated_at` | 用 `[t,t+C)` 真值 |
| `load` | canonical `system_load_mw` | B：同上 | **全零数组**（当前 `snapshot_adapter.py:129` 行为） |
| `temperature` | canonical `temperature_deg_c` | B：persistence / 日周期 | 用 `[t,t+C)` 真值 |
| `ghi` | canonical `ghi_w_per_m2` | B：日周期（晴天包络）+ 保守上界 | 当作 PV 发电量 |
| `wind_speed` | canonical `wind_speed_10m_mps` | B：persistence | 当作**风电发电量**（`wind_generation_kw` 仍 unavailable） |
| `carbon` | **无** | **无**（保持 unavailable） | 常数或默认日曲线 |
| `arrival` | **无** | **无**（保持 unavailable） | 用已抽样出的未来真实任务序列生成正式 forecast |

**口径硬规则**：**不得**把 canonical truth 直接切 `[t, t+C)` 后称为 forecast。
正式链必须能机器判定每个 forecast 序列属于 {external, modeled, persistence,
oracle_debug}，且 `oracle_debug` **不可用于正式训练/评估**。

### 6.2 必须回答的问题

1. **`build_scenario()` 返回 forecast 还是同时管理 truth artifact？**
   建议：`build_scenario()` 只返回 **forecast + provenance**（供 observation/planner）；
   **truth 由独立的 `load_truth_artifact(split)` 提供**，只有 env 的 `step()` 与
   评估器可访问。两者**不得**是同一个对象或同一 dict 的切片。

2. **执行用 truth 与 observation/planner 用 forecast 如何物理隔离？**
   建议：`ScenarioBundle` **不含** truth 字段（本卡已确认它没有）；
   truth 走独立 artifact + 独立 loader，且在 env 内以**不可从 observation 路径到达**的
  属性持有；用一个**结构性测试**断言「观测/快照对象图上不存在对 truth 数组的引用」。

3. **`start`/`horizon` 越界如何 fail closed？** 建议：切分 manifest 记录每段的
   `[start, end)`；越界、跨界或 `t + H > split_end` 一律 `ValueError`，不截断、不环绕。

4. **三者 hash 互校**：`split manifest` 记 canonical parquet 的 sha256；
   `forecast artifact` 记 split manifest 的 sha256 + 自己的 sha256；

## 7. 契约变更判断与后续卡拆分

### 7.1 需要 contract-v8 吗？—— 需要；附完整影响面与更窄的替代方案

`ScenarioBundle` 缺少 §2.4 表中 6/7 项 provenance，且**无法**逐序列区分
external / modeled / persistence / oracle_debug。两条路径：

**路径 1（推荐）：bump `CONTRACT_VERSION_ID` → `contract-v8`，扩展 `ScenarioBundle`。**

影响面（**本卡不执行**，仅登记）：

| 影响面 | 说明 |
|---|---|
| `contracts/__init__.py:9` | 单一版本源 `CONTRACT_VERSION_ID`（全仓共用） |
| 全仓引用点 | `grep -rl "CONTRACT_VERSION_ID"` ≈ **50 个文件**（契约、scenario、safe_rl_v2、大量 tests） |
| rollout buffer | v7 buffer 因版本不符**全部失效**（既有的、预期的行为） |
| checkpoint | v7 checkpoint 全部拒绝加载（预期的红线行为） |
| `content_hash()` | `ScenarioBundle.content_hash()` 覆盖 model dump，新增字段会改变所有已记录 hash |
| 现有测试 | 依赖版本字符串的测试需同步更新；**不得**为转绿而放宽断言 |
| 迁移成本 | 一次性、可回滚（单卡内完成），但**必须**与 M1.3e 的 leakage 测试重写同卡 |

**路径 2（更窄）：不 bump 版本，新增**独立**契约（如 `ForecastProvenance`），
`ScenarioBundle` 仅新增一个**可选**字段引用它。**

| 优点 | 缺点 |
|---|---|
| 不使 v7 buffer/checkpoint 失效；影响面小得多 | `ScenarioBundle` 形状**仍然**变化（新字段），严格说仍是一次 schema 变更 |
| 可先落地 provenance，把版本 bump 留到真正不兼容时 | 仓库纪律是「单一版本源」，绕过它会削弱「任何 schema 变化都显式」的可审计性 |

**推荐路径 1**：本仓库的既定纪律是 `CONTRACT_VERSION_ID` 为**唯一**版本源、
任何 schema 变化都显式化。既然 `ScenarioBundle` 形状必然变化，就应当诚实地 bump，
并把 buffer/checkpoint 失效当作**预期代价**（与既有 v6→v7 的处理一致）。
