### c.1 formal `ScenarioBundle` 在 origin=t 时，七类 forecast 如何只用 t 前可得信息

对**全局 origin = i**（`i = _origin_index(split, t)`，`scenario/splits.py:294`），
七条序列的**唯一**合法来源如下。共同约束：`generated_at = target_start =
information_cutoff_exclusive = canonical[i]`，`target = [i, i+C)`，
`lookback = [i−48, i)`，且 `generated_at` 七项恒等（`contracts/models.py:366-382`）。

| # | 序列 | `source_kind` | 唯一信息来源 | 是否读 `[i, i+C)` 真值 |
|---|---|---|---|---|
| 1 | `price_forecast` | `seasonal_naive` | M1.3e provider，`forecast[k]=price(i+k−48)` | **否** |
| 2 | `load_forecast` | `seasonal_naive` | 同上（`system_load_mw`） | **否** |
| 3 | `temperature_forecast` | `seasonal_naive` | 同上（`temperature_deg_c`） | **否** |
| 4 | `wind_forecast` | `modeled_scenario` | 由 #3 的因果 `wind_speed_10m_mps` forecast 逐点过 `wind_generation_kw()` | **否**（§c.2） |
| 5 | `pv_forecast` | `modeled_scenario` | 由 #3 的因果 GHI / 温度 / 风速 forecast 逐点过 `local_pv_kw()` | **否**（§c.2） |
| 6 | `carbon_forecast` | **待人工裁决** | v2 驱动表常数 0.402（B1 批准） | **否**（常数） |
| 7 | `arrival_forecast` | `modeled_scenario` | v2 冻结 48 槽 template + `Poisson(template×1000)`，seed `20240916` | **否**（§c.3） |

**「只用 t 前可得信息」的机械判据**（M1.3g-b 必须先红测试）：

1. 七条序列的 provenance 的 `information_cutoff_exclusive` **全部等于 origin**；
2. 对 `[i, i+C)` 之内**任何** canonical 数值做 mutation（并同步更新两个 manifest 的
   hash，使信任链自洽），**七条 forecast 逐位不变**；
3. 对 `[i−48, i)` 之内**任一** driver 数值做 mutation，**对应的 forecast 必变**。

> ⚠️ **第 2 条必须作用在 formal 构造器上**，而不是像 M1.3e 那样只作用在纯函数
> `seasonal_naive_forecast` 上：M1.3g 新增的 PV / 风电 / carbon / arrival 四条
> 是**新的**计算路径，它们各自都需要自己的 leakage 回归。

### c.2 GHI / 温度 / 10 m 风速的 causal forecast 如何推导 PV / 风电 forecast

**核心结论：PV 与风电 forecast 是五个 driver forecast 的「逐点确定性变换」，
因果性由构造继承，不需要任何新的历史窗口。**

```text
# origin = i；C = forecast_cutoff；ts = target_timestamps（已知的未来日历时刻）
ghi_f[k]  = seasonal_naive_forecast(ghi_w_per_m2,      origin=i, cutoff=C)[k]
temp_f[k] = seasonal_naive_forecast(temperature_deg_c, origin=i, cutoff=C)[k]
v10_f[k]  = seasonal_naive_forecast(wind_speed_10m_mps,origin=i, cutoff=C)[k]

pv_f[k]   = local_pv_kw(times=[ts[k]], ghi=[ghi_f[k]],
                        temp=[temp_f[k]], wind=[v10_f[k]])[0]
wind_f[k] = wind_generation_kw(wind_speed_10m_mps=[v10_f[k]])[0]
```

**为什么这**不**构成泄漏**：

1. `ghi_f[k] = ghi_truth(i + k − 48)`，即**只**读取 `[i−48, i)` —— 由
   `scenario/forecast.py:177-190` 的 `history_start = origin - period_steps` 保证；
2. `ts[k]` 是**未来日历时刻**，不是未来真值；太阳位置
   （`solarposition.get_solarposition`，`scenario/exogenous_drivers.py:283`）与
   时刻槽（`arrival_template_slot`，`:550-553`）都是**天文/日历的确定性函数**，
   在 origin 时刻本来就完全已知；
3. `local_pv_kw()` / `wind_generation_kw()` 是**逐点纯函数**，没有跨时间聚合、
   没有滑动窗口、没有对整条序列的统计量 —— 因此单个 `k` 的输入只取决于
   `ghi_f[k]` / `temp_f[k]` / `v10_f[k]`；
4. 由于 1–3，`pv_f[k]` 的**全部**输入都来自 `[i−48, i)`，与 `[i, i+C)` 真值无关。

**逐点调用是与真值物化完全一致的同一实现**：`scenario/exogenous_drivers.py:240-264`
与 `:429-439` 的签名对单点输入同样成立，因此 **A/B 对照可直接做**：
把真值序列喂进去得到 v2 驱动表；把 forecast 序列喂进去得到 formal forecast。
两者共用同一份物理代码，**不存在第二套 PV/风电实现**。

**必须显式记录的边界**：

- PV 的 `pv_ac_limit_kw`（`:169-176`）与风电的 `rated_capacity_kw`（`:400`）
  仍然生效 —— forecast 也**不得超过** 416.6667 kW / 800 kW；
- 夜间（`ghi_f[k] <= 0`）必须严格为 0（`:230-231`）；
- 若 `forecast_cutoff C > 0` 但 `ghi_f` 非有限，必须 fail closed，不得零填。

### c.3 carbon 常数与 date-free arrival 的 formal provenance 如何表达

**carbon**（`scenario/exogenous_drivers.py:89-92`，B1 批准）：

- `forecast[k] = 0.402`（全部 k），**逐位等于**真值表的 carbon 列；
- `information_cutoff_exclusive = origin`（诚实声明：常数在 origin 已知）；
- `lookback_start` = `origin − 48` 步（与其它序列**口径一致**，便于统一校验）；
- `seed = null`（确定性）；
- **待裁决**：contract 的 `SOURCE_KINDS`（`contracts/models.py:44-47`）里
  **没有** `human_approved_external_low_resolution` 这个值，而
  `MODE_ALLOWED_SOURCE_KINDS["formal"]`（`:62-68`）只允许
  `external_forecast` / `seasonal_naive` / `persistence` / `modeled_scenario`。
  M1.3f-c 的裁决又明确要求 carbon **不得**写成 `modeled_scenario`。
  → **三选一必须由人工裁决**（见 §c.7 D1），**不得由实现自行选择**。

**arrival**（`scenario/exogenous_drivers.py:550-605`，B5-ARRIVAL 批准）：

- `slot = hour*2 + minute//30`（`arrival_template_slot`，**不读星期**）；
- `rate = frozen_template[slot] × 1000.0`；`forecast[k] = Poisson(rate; seed=20240916)`；
- **因果性由「不读任何 2024 数值」保证**：template 来自 Azure 2019 benchmark trace，
  seed 固定，slot 只由 `target_timestamps[k]` 的 hour/minute 决定；
- `generated_at = origin`、`lookback = [i−48, i)`；
- **必须逐位可复现**：同一 origin + 同一 template + 同一 seed → 同一数组；
- **注意 RNG 顺序**：`generate_arrival` 一次调用对整条 `timestamps` 前向采样
  （`:599-602`）。若 formal 路径对每个 origin **单独**调用（每次只喂 C 个时刻），
  则每个 origin 的随机流从 seed 重启，**结果与「一次性生成全年」不同**。
  这在因果上**无害**（不读未来），但必须在 manifest 中**明确登记**所采用的口径，
  否则同一份数据会有两种「正确」答案。→ 见 §c.7 D3。

### c.4 train / validation / test manifest 的精确职责

三个保留名是**同一 schema 的三份实例**，职责是「**声明这条链是怎么冻结的**」，
而**不是**存放数据本身：

| 职责 | 内容 |
|---|---|
| 1. 切分声明 | `split`、canonical 行区间 `[row_start, row_end)`、起止时间戳 |
| 2. origin 策略 | `H`（episode 长度）、`C`（forecast cutoff）、允许的 origin 集合或生成规则 |
| 3. 四层信任链 | canonical parquet / canonical manifest / split manifest / exogenous v2 驱动表的 path + SHA-256 |
| 4. forecast policy | `singapore_2024_forecast_policy.json` 的 path + SHA-256 |
| 5. refs 冻结 | `configs/frozen_refs/refs.json` 的 path + SHA-256（**train 生成的同一份**） |
| 6. readiness | 明确布尔量，且**不得**预先声称 formal 训练就绪 |

**必须遵守**：

- 三份 manifest **不得**内置任何 forecast 数值（那些由 causal provider 在调用时生成）；
- 三份都必须引用**同一份** `refs.json` 的**同一** hash（§c.5）；
- 缺失、hash 不符、schema 未知 → fail closed，**不截断、不换段、不回退 synthetic**；
- 创建这三份文件**本身**必须是一张独立卡（M1.3g-c），且只有在该卡的最终
  HEAD 上生成一次，**不得**在实现未冻结前预先创建。

## q. M1.3g-d-R1：移除 refs 冻结的 frame 注入信任边界漏洞

### q.0 元信息

| 字段 | 值 |
|---|---|
| 返修卡 | **M1.3g-d-R1** |
| 强制起点 SHA | `e89c15c` |
| 审核结论 | **不通过**：公开入口可通过 `canonical_frame=` 注入**未经 manifest / hash 验证**的 DataFrame，且 `materialize_frozen_refs(..., **build_kwargs)` 会把它**透传到写盘路径** |
| 状态 | 执行中 |

### q.1 已复现的缺陷（审核方与本卡各自实测）

```python
frame = pd.read_parquet("data/processed/singapore_2024/half_hour.parquet")
frame.loc[frame.index[0], "price_sgd_per_kwh"] = 99.0
materialize_frozen_refs(out_path=<tmp>/"refs.json", canonical_frame=frame)
# → written: True
# → refs.json 的 references.price_ref.value == 99.0
```

**后果**：`build_frozen_refs` / `materialize_frozen_refs` 的 `canonical_frame`
参数绕过了 canonical parquet ↔ canonical manifest ↔ split manifest 的**全部**
hash 校验；`materialize_frozen_refs(..., **build_kwargs)` 让这个绕过直达
**写盘**。因此 **v2 refs 不能作为后续正式证据**。

### q.2 必须修复

1. **公开签名**不得含 `canonical_frame` / 任意 DataFrame / `expected_*` /
   信任根 override / `**kwargs`。传这些参数必须 **`TypeError`**。
2. 拆出的**纯计算函数只能是私有函数**；它接收的 frame 必须已由**公开入口**
   完成完整验证。
3. **`iloc` 切片之前**必须严格校验 canonical 与 exogenous：
   - 行数相同；
   - 都有 `timestamp` 且**均 tz-aware**；
   - 无重复、严格递增、严格 **30 分钟**网格；
   - **逐行 timestamp 完全相等**；
   - train 所需列存在且**数值有限**。
   任一失败必须 `ValueError` / `SplitError`，**不泄漏** `KeyError` /
   `TypeError` / `IndexError`。
4. train-only 推导的验证必须走「**完整临时冻结信任链 + 公开文件路径入口**」，
   **不得**借 `canonical_frame` 或 monkeypatch 验证器。
5. 现有 `configs/frozen_refs/refs.json`（v2）**逐字节不变**，文档标
   **`superseded_pre_trust_boundary_fix`**；生成新的
   **`configs/frozen_refs/refs_v3.json`**；**后续 g-c 只能引用 v3**。
6. v3 的 **refs 数值必须与 v2 相同**；`materializer_revision` 必须反映
   **R1 实现**。schema、逐值 provenance、原子性、幂等、防覆盖与
   dirty-generator 拒绝**全部保持**。
7. 测试不得存在任何**测试专用** trust-root / hash / revision / frame 注入。
