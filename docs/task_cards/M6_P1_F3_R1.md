### 7.4 根因（**修正后的归因**）

**到期不可中断任务的逐任务分配（origin 48 / step 4，直接取出）**：

```text
任务             剩余    期限   StageA_step0  StageB_step0   StageA_deadline_slack
0               21.48    24      21.4821       21.4821        0.0000
47396540601128   0.00     2       0.0000        0.0000        0.0000
42273281206793   0.00     3       0.0000        0.0000        0.0000
25152242906001   3.52     4       3.5179        3.5179        3.5179   ← 到期不可中断任务
19867396192526   0.00     5       0.0000        0.0000        0.0000
非零组 StageA = [8, 12, 14, 15]，值 [1.000, 0.047, 1.000, 1.000]
非零组 StageB = [8, 12, 14, 15]，值 [1.000, 0.047, 1.000, 1.000]   ← 逐位相同
```

**关键事实**：**两阶段都给到期不可中断任务分配了它的全部剩余工作 3.5179**
（stage A 与 stage B **逐位相同**），且**两阶段的逐组动作与非零组完全相同**。

⇒ **服务损失既不是阶段 A 造成的，也不是阶段 B 改变分配造成的**：
规划器（两阶段）已经把该任务**足额**安排了。**§7.2 的「稀疏分配在阶段 A 形成」仍然成立**，
但它**不是**服务损失的成因——稀疏本身没有剥夺该任务的规划工作。

**真正的根因（修正）**：corrector 交回环境的只是**逐组容量信号**
`u_g`（→ `planned_capacity_vec[g] = action[g] × …`）；**规划器内部的逐任务分配
`A[i,g,0]` 不会传给环境**。环境随后用**自己的**任务分配规则、仅在那 **4 个非零组**
的容量内重新决定「哪个任务拿工作」。因此：

1. raw 提案是「20 组全 1.0」，env 的分配器有全部 20 组可用；
2. corrector 的 exec 只剩 **4 组**（`Σu = 3.0468`），env 的分配器可用的服务器组骤减；
3. 规划器**本想**服务的到期不可中断任务，在 env 的重新分配中**落空** ⇒ 记为不可中断中断；
4. corrector off 时 raw（20 组全 1.0）直接进 env ⇒ 服务完美、两种模式物理违规均为 0。

**结论**：瓶颈在 **corrector → env 的接口信息量**——逐组动作的**稀疏化**（L1 目标在
同一 `Σu` 下不区分组间分布，落到顶点解）使 env 侧可用组数从 20 降到 4。
**未定位**：env 侧分配器在这 4 组下具体按什么规则落在别的任务上（需另一步骤追踪
env 的 `_allocate_*`）。
