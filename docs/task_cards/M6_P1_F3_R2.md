### 7.2 **根因（实测确认，2026-09-28）**

**step 3 分配链实测**：

```text
分配器输入顺序（priority↓, deadline↑, arrival↑, id）：
   id=4227328120679301816 prio=3.314 deadline= 3 arrival=1 rem= 0.000 max_rate=36
   id=473965406011283739  prio=2.765 deadline= 2 arrival=0 rem= 0.000 max_rate=38
   id=2515224290600144462 prio=2.688 deadline= 4 arrival=2 rem=10.518 max_rate=32   ← 到期任务
   id=0                   prio=1.000 deadline=24 arrival=0 rem=21.482 max_rate=50
计划容量（非零组）= {8: 8.240, 12: 7.398, 14: 8.457, 15: 7.905}   合计 = 32.0000
allocate_tasks(上述输入, 计划容量) 输出：
   {'42273281206793': 0.0, '47396540601128': 0.0, '25152242906001': 10.518, '0': 21.482}
   ⇒ **分配器本身给足到期任务 10.518**（它并不是丢失环节）
```

**真正原因——快照任务集与 `env.step()` 当步激活后的任务集不同**：

```text
快照任务 id 数 = 4        step 前 env 已激活 = 4        （同一时刻比较确实相同）
step 3 当步到达的任务数 = 1
   新到达 id=1986739619252678150  workload=25.000  获得=25.000
到期任务 step3 实得 = 7.0000（计划 10.5179）
step3 全体实际完成 = 32.0000（= 计划容量合计 32.0000）
```

⇒ **3.5179 去了「step 3 当步到达的任务 `1986739619252678150`」**：它带着
workload 25.0 在**该步开始时**被环境激活并按分配器排序（priority 更高）**优先取走 25.0**，
只剩 7.0 给到期任务。**总量没有浪费**（32.0 = 计划容量），是**再分配**的结果。

**口径差异**：`planning/snapshot_adapter.py` 的 `TaskState` 过滤条件是
`task.status != "not_arrived"`，而 `arrival_time == current_step` 的任务在**建快照时**
尚未被 `_activate_arrivals` 激活 ⇒ **规划器看不见当步到达的任务**，于是把全部 32.0 容量
排给了它看得见的 4 个任务；而环境在该步服务那 5 个任务，新到达者优先级更高、
先取走 25.0，把到期任务挤到 7.0。**这不是未来信息泄漏**——当步到达的任务在该步本就可观测
（环境自己在 step 开始时就激活它们）。

**最小修复方向**：让快照把**当步到达**（`arrival_time <= current_step`）的任务一并纳入
`TaskState`，使规划器与分配器的任务集口径一致。（本会话到上下文上限，**未实施**。）
