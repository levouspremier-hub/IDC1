### 7.2 **根因（实测确认，2026-09-28）**

**step 3 分配链实测**：

```text
分配器输入顺序（priority↓, deadline↑, arrival↑, id）：
   id=4227328120679301816 prio=3.314 deadline= 3 arrival=1 rem= 0.000 max_rate=36
   id=473965406011283739  prio=2.765 deadline= 2 arrival=0 rem= 0.000 max_rate=38
   id=2515224290600144462 prio=2.688 deadline= 4 arrival=2 rem=10.518 max_rate=32   ← 到期任务
   id=0                   prio=1.000 deadline=24 arrival=0 rem=21.482 max_rate=50
计划容量（非零组）= {8: 8.240, 12: 7.398, 14: 8.457, 15: 7.905}   合计 = 32.0000
allocate_tasks(上述输入, 计划容量) 输出：
   {'42273281206793': 0.0, '47396540601128': 0.0, '25152242906001': 10.518, '0': 21.482}
   ⇒ **分配器本身给足到期任务 10.518**（它并不是丢失环节）
```

**真正原因——到达激活发生在「处理该步」而不是「进入该步」**：

> ⚠️ **R2 续作更正（2026-09-28，实测）**：本段初版写的「快照任务集与 `env.step()`
> 当步激活**后**的任务集不同」**不准确**。实测：建快照时（`env.step()` **之前**），
> `snapshot.tasks`（判据 `status != "not_arrived"`）与 env **当时**已激活的任务集
> **逐 id 相同**（都是 4 个，含 2 个 `remaining_work == 0` 的已终结任务）。
> 真正的差异是：`env.step(t)` 会在**分配之前**先执行 `_activate_arrivals(t)`
> （`envs/idc_price_env.py:797`），把 `arrival_time == t` 的任务置为 `waiting`，
> 于是**同一决策步的分配器**看到的任务集比**观测与快照**多出当步到达的那一个。

```text
决策步 t 的三方口径（修复前）：
  观测   `_get_task_pool_features(t)` 判据 = arrival_time <= t   ⇒ 含当步到达任务（但 status 仍 not_arrived，
                                                                  落入 waiting/running/unfinished **任一子集之外**）
  快照   `planning/snapshot_adapter.py`  判据 = status != not_arrived ⇒ **不含**当步到达任务
  分配器 `_execute_tasks_action_guided` 判据 = status ∈ {waiting,running,paused}，且在本步开头激活**之后**构造
                                          ⇒ **含**当步到达任务
```

```text
step 3 实测（origin 48 / compute 1.0 / corrector on，修复前）：
  快照任务 id 数 = 4（0 / 2515224290600144462 / 4227328120679301816 / 473965406011283739，
                     后两个 rem=0 已终结）      step 前 env 已激活 = 同样这 4 个
  step 3 当步到达的任务数 = 1
     新到达 id=1986739619252678150  workload=25.000  获得=25.000
  到期任务 step3 实得 = 7.0000（计划 10.5179）
  step3 全体实际完成 = 32.0000（= 计划容量合计 32.0000）
```

⇒ **3.5179 去了「step 3 当步到达的任务 `1986739619252678150`」**：它带着
workload 25.0 在**该步开始时**被环境激活并按分配器排序（priority 3.1723 > 到期任务
2.6882）**优先取走 25.0**，只剩 7.0 给到期任务。**总量没有浪费**（32.0 = 计划容量），
是**再分配**的结果。

**"这不是未来信息泄漏"的证明**：`arrival_time <= current_step` 的任务在该步本就可观测
（环境自己在该步开头就激活它们，`reset()` 也在生成 t=0 观测**之前**激活
`current_time=0`）；`arrival_time > current_step` 的任务仍保持 `not_arrived`，
不进入观测、快照或分配器。该命题由
`tests/test_m6p1f3r2_decision_task_state.py::test_decision_step_exposes_no_future_task`
在 origin 48 / 4848 的**每一个决策步**上断言（环境侧与快照侧同时检查），故不再是未经证明的说法。

**实际修复（已实施，非「只改快照过滤条件」）**：把「到达激活」归位为
「**进入**某一步」——在 `envs/idc_price_env.py::step()` 的 `current_step += 1`
之后、生成该步观测之前调用 `_activate_arrivals(current_step)`，并同步重算
`Q_t = _compute_backlog_work()`。观测、快照、分配器因此共用**同一份**可见任务状态。
**未**单独放宽快照过滤条件。

### 8.2 时序核对（决策步 t 的任务何时可见）

```text
reset()                : current_step=0 → _activate_arrivals(0) → Q_t=_compute_backlog_work() → _get_obs()
step()  修复前          : _activate_arrivals(t) → 物理投影 → 分配（active_tasks）→ … → current_step+=1
                         → Q_t=Q_next → _get_obs()          ← 观测在**下一步**激活之前生成
step()  修复后          : 同上，但在 current_step+=1 之后、_get_obs() 之前插入
                         _activate_arrivals(current_step) + Q_t=_compute_backlog_work()
```

| 通道 | 判据 | 修复前决策步 t 是否含 `arrival_time == t` 的任务 |
|---|---|---|
| 观测任务池 `_get_task_pool_features(t)` | `arrival_time <= t` | 计入 `arrived_tasks`，但 status 仍 `not_arrived`，落入各子集之外 |
| 观测队列 `Q_t` | `status ∉ {finished, not_arrived}` | 否 |
| corrector 快照 `snapshot_adapter` | `status != "not_arrived"` | 否 |
| 环境分配器 `active_tasks` | `status ∈ {waiting,running,paused}`（本步开头激活**之后**） | **是** |

修复后四条通道全部等于 `arrival_time <= current_step` 的未终结任务集（观测队列
`Q_t == _compute_backlog_work()` 亦由
`test_queue_amount_matches_visible_backlog` 逐步断言）。
