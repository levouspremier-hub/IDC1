## 1. 目标

1. **泄漏门禁**：用真实 `IDCPriceEnv20D` 证明当前时刻可见窗口之外的未来真值
   （price / temperature / lambda / PV / wind / carbon）被逐项突变后，
   当前 `observation`、`raw_action`、`old_raw_log_prob` **逐位不变**；
   并证明改动**窗口之内**的值时 observation **会**变化（反例，防恒真）。
2. **可复现性**：corrector **关闭** 的跨进程语义摘要逐位一致
   （排除纯耗时字段）。

**⚠️ 已登记的 blocker（实测推翻了原假设）**：任务卡原以为
「正常预算开启」也可逐位复现、只有**紧预算**不稳定。实测表明
**corrector 开启的任何非恒超时预算都不稳定**（含正常预算 `0.05`），
且原因是**多最优解**（求解器收敛了，但不同进程走到不同最优顶点），
不是超时退化。故本卡**只对 corrector 关闭**断言可复现，
对 corrector 开启**不做任何相等断言**。详见 §3。

## 3. 已登记的 blocker：corrector **开启**时跨进程**不可复现**（实测）

corrector 是**有时限的 MILP**。时限内走到哪一个最优解取决于求解路径，
而**多个最优解的元素可以不同**（同代价、均已通过物理校验）。
因此 corrector 开启时 exec 决策随进程/负载变化。

实测（同一份代码、同一 seed；比较**排除** `correction_solve_time_s` /
`stage_a_solve_time_s` / `stage_b_solve_time_s` 后的语义 sha256）：

| 情形 | 各进程摘要 | 相异数 | `correction_reason` |
|---|---|---|---|
| **corrector 关闭**，10 进程（含 6 路 CPU 争用） | `a0d22d1fdcf5` ×10 | **1** | — |
| corrector 开启 `0.05`（**正常预算**），6 路 CPU 争用、4 进程 | `8468db982fa6` ×2、`842b06d3bf97` ×2 | **2** | 全部 `none`（**求解器确实收敛**） |
| corrector 开启 `0.05`，**无负载** 2 进程 | `8468db982fa6`、`28258c1a5eba` | **2** | 全部 `none` |
| corrector 开启 `0.020`，争用、4 进程 | 3 种 | **3** | 含 `none` 与 `timeout` |
| corrector 开启 `0.010`，争用、4 进程 | 2 种 | **2** | `timeout` |
| corrector 开启 `0.005`，争用、4 进程 | 2 种 | **2** | `timeout` |
| corrector 开启 `0.003`，争用、4 进程 | 1 种 | 1 | 恒 `timeout` → 恒返回边界动作，**反而确定** |

**关键点：连「正常预算」都不稳定，且 `correction_reason` 是 `none`。**

这不是超时退化，而是**多最优解**问题：求解器收敛了，但不同进程走到了**不同的最优顶点**，
元素不同、代价相同、且都通过了物理校验。所以本卡最初的假设
（「只有紧预算不稳定」）**被实测推翻**，blocker 的范围**扩大**为「corrector 开启的
任何非恒超时预算」。

**结论与处置**：

- 只对 **corrector 关闭** 断言跨进程逐位一致（10/10 实测，含负载）；
- 对 corrector 开启**不做任何相等断言**，也**不重试挑选取样**；
- 按任务卡要求**登记为 blocker 并停止**对 corrector 开启稳定性的一切声称。

**为什么不在本卡修复**：消除该不确定性需要改变 `planning/` 的求解器策略
（固定求解路径、消解最优解平局，或改用确定性求解配置），
**超出本卡允许范围**，且会改变研究语义（属于后续工作）。
本卡**未修改** `rollout.py` 或 `corrector_wrapper.py`。

### 10.3 泄漏门禁结果（真实 env、显式三类 seed、显式 generator）

| 检查 | 结果 |
|---|---|
| 六类未来真值在 `[cutoff + steps, horizon)` 整体突变 → observation / raw_action / old_raw_log_prob / reward 逐位不变 | ✓ |
| 窗口**之内**（`cutoff - 1`）突变 → observation 与 raw_action **必须变化**（反例，证明门禁非恒真） | ✓ |
| 边界语义：从 `cutoff` 起突变不改第 0 步观测；从 `cutoff - 1` 起必须改 | ✓ |
| **逐数组**独立门禁 + 各自反例（5 个进入观测的阵列） | ✓ |

**重要发现：可见窗口是滑动**的 —— 第 `t` 步可见 `[t, t + cutoff)`。
因此长度为 `steps` 的 rollout，其真正安全的突变区间是
**`[cutoff + steps, horizon)`**；只从 `cutoff` 起突变只能保护**第 0 步**。
（第一次写测试时按 `[cutoff, horizon)` 突变，第 1 步起的观测就开始变化；
已据此修正。）

**第二项发现：`lambda_t` 不进入 observation。** 实测「窗口内突变是否改变观测」：

| 阵列 | 窗口内突变影响 obs | 窗口外突变影响 obs |
|---|---|---|
| `price_t` / `T_amb` / `pv_t` / `wt_t` / `carbon_factor_t` | **True** | False |
| `lambda_t` | **False** | False |

故对 `lambda_t` 的泄漏门禁是**空真**的（从不被读取的量不可能泄漏），
也无法为它构造「窗口内突变必须改变观测」的反例。已拆成
`OBSERVED_TRUTH_ATTRS`（5 个）与 `NON_OBSERVED_TRUTH_ATTRS`（`lambda_t`），
并用一条测试固定后者「不进入观测」的事实 —— 若将来 lambda 被接进观测，
该测试会失败并提醒补上反例。
